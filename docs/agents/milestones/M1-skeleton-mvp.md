# M1: Skeleton MVP

## Goal

A contributor can open the repository in the devcontainer, build `releash`, and run it to see general help. The CLI does nothing else yet, but every pull request is already linted, built and tested in CI.

## Scope

Specs (in `docs/specs`) delivered by this milestone. Check each off when it is implemented.

- None. M1 is groundwork for [0001-rollout-decisions](../../specs/0001-rollout-decisions.md), which is delivered by M3 and M4.

## Exit criteria

- The devcontainer is generated by gantry from the `ivanklee86/devcontainers` Go base plus a `.devcontainer/releash.libsonnet` overlay, following argonap and tangle. Regenerating `devcontainer.json` gives no diff, and the image builds.
- The Go module `github.com/ivanklee86/releash` follows [Organizing a Go module](https://go.dev/doc/modules/layout) and argonap's CLI pattern:
  - `main.go` at the root holds only the cobra wiring: it maps options into a config and calls the orchestrator. `go install github.com/ivanklee86/releash@<version>` works because of this.
  - `internal/releash` holds the orchestrator: a `Releash` type built with `New` or `NewWithConfig(Config)`, with swappable `Out` and `Err` writers. Its methods do everything the CLI does and return the exit code instead of calling `os.Exit`, so tests can drive it directly.
- The CLI is built on cobra, with viper wired in through the existing flag-binding code from create-a-ci, both at pinned versions.
- `releash` with no arguments and `releash --help` print general help to stdout and exit 0.
- `releash --version` prints the version and exits 0. The version is the one injected at build time if there is one. Otherwise it is the main module's version from Go's build info, which is the module version for `go install` and a VCS pseudo-version for `go build` in a git checkout. If neither is available, it is `dev`.
- An unknown command or option prints an error to stderr and exits 2, matching [ADR 0004](../../adrs/0004-exit-code-contract.md). stdout is empty: the `true`/`false` stdout contract in spec 0001 covers `releash check` only, which arrives in M3.
- `go build ./...` and `go test ./...` pass, with tests covering the four behaviours above.
- `Taskfile.yaml` includes `tasks/go.yaml`, following argonap, with `install`, `install-ci`, `fmt`, `lint`, `build` and `test`. `task` with no arguments runs format, lint, build and test.
- golangci-lint, pinned to the version in the devcontainer base image, runs with an explicit `.golangci.yml` (argonap's `standard` linter set, plus the `gofmt` and `goimports` formatters required by AGENTS.md), and the code passes it.
- `.github/workflows/ci.yaml` follows argonap's: least-privilege `permissions`, PR runs cancelled when superseded, and `lint` (gofmt check, `task go:lint`, `task go:build`) and `test` (`task go:test`) jobs. Task is installed through a copy of argonap's `.github/actions/setup-task` composite action at a pinned version, and Go tool binaries are cached. CI passes on the M1 pull requests.
- `docs/agents/internals.md` describes the layout.

## Out of scope

- prek hooks, Renovate, the compose stack, integration tests, and CI's prek, integration, test report and coverage jobs (M2).
- The `check` command and every option from spec 0001 (M3).
- The Unleash SDK and anything that talks to Unleash (M4).
- Releases: goreleaser, published binaries and container images (M5).
- Pretty printing or styled output. releash prints very little, so plain text is enough.

## Risks / open questions

- CI runs on GitHub Actions in `ivanklee86/releash`. Actions must be enabled with permissions that allow the workflow's `permissions` block.
